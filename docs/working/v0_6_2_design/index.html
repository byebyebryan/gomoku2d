Gomoku2D / 0.6.2 / design exploration

A player page that belongs in the game.

Three compositions, the same content, the existing visual language. Start with A, then compare B and C with one game and statistics hidden.

Prototype study · synthetic data · no account, cloud writes, or production changes. A direction is recommended, not adopted.

01

The shell is missing

The current page is an 820px card with its Home action at the bottom. Match, Replay and Profile establish a stronger header and visible navigation.

02

Games need priority

Five statistic boxes and a large disclaimer sit before the game list. Divided rows and a quieter record make the games easier to reach.

03

Sparse is a real state

A profile can have one game, no shared statistics, or no games at all. Its composition should work without avatars, a bio or invented statistics.

Recommendation for discussion

Start with A. Borrow B's continuity with Profile.

A gives the player a proper app header, reduces repeated boxes, and keeps games prominent whether statistics are shared or hidden. B makes the relationship to My games most explicit, but its identity column can become an under-filled rail. C is restrained and easy to scan, though it retains more of the standalone-card character.

A · Wide record

Full-width name and navigation, a quiet shared record, then a divided game list. Best balance of sparse and full states.

B · Profile columns

Identity and record on the left, games on the right. Familiar app structure; less horizontal room for long game titles.

C · Compact record

Name, compact record and games inside one panel. More contained, with less use of a large desktop viewport.

Choices to settle: composition A/B/C, shared-record density, disclosure placement, and whether the visitor should have a Copy link action. The content and manually refreshed statistics remain the same. Thumbnails are a later enhancement.

Research and constraints

  • The strongest visual references are our own Profile, Settings, Replay and Rules surfaces. The study copies the current global stylesheet, actual PixelOperator fonts and existing 24px SVG icons into its export.
  • Chess.com Game Collections keeps game curation near Analysis and makes visibility explicit. This supports clear reader/owner roles; it does not justify folders or a community catalog here.
  • W3C consistent navigation informs stable control placement. W3C reflow guidance informs narrow/enlarged-text checks. Prototype checks are not human accessibility or device acceptance.
  • A live Lichess profile returned HTTP 403 during research, so it is not treated as an inspected visual reference. No competitor profile screenshot is implied.
  • No new public fields, schema changes, avatars, bios, ratings, game dates, featured games, background listeners or services. Existing snapshot date and all five current statistics remain visible when shared.
